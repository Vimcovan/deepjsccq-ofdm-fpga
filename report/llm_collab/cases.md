# 大模型协作典型案例

每个案例按"场景 → 提示 → AI 的做法 → 纠错 → 结果"整理。引号内为原话（仅删去无关部分）。出处为
`transcripts/` 下的会话文件与时间（UTC）。

参与者：**参赛者**（提出目标、约束、关键判断，负责接线、上电等物理操作）；**Claude Code**（AD9361 / OFDM PHY、
PYNQ 软件、GUI、测量、演示视频、仓库与报告）；**Codex**（DeepJSCC-Q 训练与量化、网络 RTL 生成器与验证、网络部分论文草稿）。

## 一、射频前端与物理层（Claude Code）

### 1. SPI 握手错位：先确认配置"真的执行了"

- **场景**：单板环回 EVM 只有 −22 dB，原因不明（`claude/AD9361_fc490b96.md`，09-25）。
- **提示**：参赛者指定 ILA 触发方式："不要使用立即触发，把触发条件设置为 rx_data=12'd1xx，因为 TX 是突发，但 RX 是一直开启的，可能会抓到静默区"。
- **AI 的做法**：离线解调抓到的帧，逐项排除噪声、信道、ISI、非线性，按镜像子载波建模定位到 IQ 失衡（镜像 −25 dBc，全频带一致）
  → 推断 TX 正交校准没生效 → 追到 `ad9361_spi.v` 不等请求就锁存命令，应答错位一拍，所有"等待校准完成"的轮询都立即通过。
- **结果**：修正握手后 EVM −22.0 → −29.7 dB；随后又补了 PL 内的 TX 正交校准相位扫描、FIR 重新设计，最终 −32 dB
  （见 `report/notes/ad9361_debug_log.md`）。
- **要点**：参赛者给出测量方法上的关键约束，AI 负责把证据链做完整。

### 2. "这是射频模块该做的事情，别去动基带"

- **场景**：两板对收时 AGC 在帧中间跳变（`claude/AD9361_d69a7c9d.md`，09-26 04:47–05:31）。
- **AI 的做法**：提出用基带的帧检测信号控制 AD9361 的 EN_AGC 引脚，在 STF 内冻结增益，并已开始给三个 RX 文件加端口。
- **纠错 1**：参赛者："不同意，这是射频模块该做的事情，别去动基带，改的乱七八糟的。"AI 撤回全部基带改动。
- **纠错 2**：AI 声称参考了 openwifi 的做法，参赛者追问："什么叫 linux 驱动代码，你真的看 openwifi-hw 了吗？里面没有写 AD9361
  寄存器吗？"AI 承认"openwifi-hw 我只搜了 `en_agc` 这一个关键字"，回去完整阅读后发现：openwifi 的 AGC 配置来自
  `agc_settings.sh`，而我们的 LUT 照抄时**漏了 0x15C、0x106、0x103、0x101 四项**。
- **结果**：补齐寄存器后稳态正常；"AGC 不与基带耦合"成为之后所有 AGC 工作的约束（案例 14 的看门狗也遵守这一点）。

### 3. LTF 定时门限：半个采样的相关峰损失

- **场景**：两板空口偶发定时锁到 LTF2 而不是 LTF1，整帧错位（`claude/AD9361_d69a7c9d.md`，09-26 08:33–08:41）。
- **提示**：参赛者给出判断："可能是因为采样相位偏移……最差的情况刚好就是相差半个采样点……你先算一下，偏半个采样点，相关峰会下降多少，
  最大旁瓣是多少，再选一个合适的阈值"，并要求"用纯移位加法实现，避免乘法"。
- **AI 的做法**：用实际前导和相关模板计算：半采样偏移时主峰 ρ² 降到 0.54（−2.66 dB），最大旁瓣 0.29（GI2 处）；参赛者取 0.375，AI 改为 `(E>>>2)+(E>>>3)`，回放出错的数据段仿真：原来锁到 LTF2 的两帧都锁回 LTF1，0 误码。
- **结果**：门限 0.375 沿用到最终版本（`report/design_report.md` 2.3 节）。

### 4. 长帧与 SFO：从 MATLAB 到 RTL

- **场景**：DeepJSCC-Q 一帧要 683 个 OFDM 符号（`claude/AD9361_d69a7c9d.md`，09-28 01:38–13:50）。
- **提示**：参赛者先问"按最坏情况（±20 ppm）最多可以传输多长的帧"，再要求先在自己的 MATLAB 接收机脚本上改、给出 RTL 的资源估计后再动手；
  并提出简化："如果你把本地 LTF 序列直接循环移位几个采样点，刚好对准需要 BACKOFF 的点数，岂不是更直接？"
- **AI 的做法**：设计逐符号导频 LS + 二阶环的跟踪式 SFO 补偿，常数乘除改为移位加减；采纳循环移位的 LTF 匹配滤波器，
  省掉回看移位寄存器；信道估计按参赛者的取舍只做双 LTF 平均。
- **结果**：±40 ppm、683 个符号仿真 0 误码；板上帧尾 EVM 与帧头只差约 1.7 dB。

## 二、网络硬件规划（Claude Code，09-28 – 09-29）

### 5. 定点方案的硬约束

- **出处**：`claude/DeepJSCC-Q_e33e691b.md`，09-28 11:01–12:12。
- **提示**："操作数位宽绝对不能超过 DSP48E2 支持范围"；"rsqrt/sqrt 完全没有必要查表，直接迭代计算就行……sigmoid 用到的地方很多，
  主要问题在于各个读口都是独立的，实际消耗的 BRAM 可能远远大于你的预估，所以我感觉 cordic 迭代或分段线性近似更好"。
- **结果**：GDN/IGDN 用迭代平方根与除法，sigmoid 用 32 段分段线性（`report/design_report.md` 2.2 节）。

### 6. "为什么 P 非要按照 BRAM 位宽去取？"

- **出处**：`claude/DeepJSCC-Q_d3a7236c.md`，09-29 02:29、08:57。
- **AI 的做法**：先按总容量估 BRAM（被追问"你不考虑读写口的吗？你觉得不同层可以共用一个 BRAM 吗？"后改为逐层按原语与端口计算）；
  随后提出"P 取最小值省 DSP、P 按 BRAM 位宽取省 BRAM"的取舍。
- **纠错**：参赛者："什么取舍？为什么 P 非要按照 BRAM 位宽去取？你是不能用 LUT 做位宽转换吗？"
- **AI 的修正**：权重读取是严格顺序的，ROM 字宽不必等于 P×8；按 BRAM 最省的形状紧密存放，读出后经 LUT 位宽转换器输出。
  "这个'取舍'其实不存在，是我把问题想窄了。"
- **结果**：DSP 与 BRAM 同时下降——编码器权重 ROM 42.0 → 38.0 BRAM36、乘累加 DSP 255 → 223；解码器 67.0 → 62.5、326 → 298
  （代价为数千 LUT；宽引擎仍直接映射）。

### 7. 自作主张的整帧 FIFO

- **出处**：`claude/DeepJSCC-Q_d3a7236c.md`，09-29 12:15–12:19。
- **AI 的做法**：在只听到"PHY 每帧图像一个突发包"后，自行假设"突发无法反压"，在编码器、解码器两端各加了整帧 FIFO。
- **纠错**：参赛者："为什么你自作主张的给编码器、解码器也加整帧 FIFO？你觉得我的 PHY 没有 FIFO 吗？"
- **结果**：网络两端改回带反压的 AXI-Stream，接口定为 24 位 {Q,I} Q10，缓冲全部交给 PHY，省掉 5 个 URAM；
  这一接口契约后来成为网络与 PHY 对接的冻结约定。

## 三、网络训练、RTL 与论文（Codex）

### 8. PSNR 上升太慢 → 量化器多乘了 `sqrt(2/42)`

- **出处**：`codex/DeepJSCC-Q_2026-09-24_*.md`，09-24 10:41–10:46。
- **提示**：参赛者观察训练曲线："不对劲，PSNR 上升太慢了，即使是之前的硬判决错误版本也没有这么慢。"
- **AI 的做法**：统计星座电平分布，发现量化前把坐标额外乘了 `sqrt(2/42)`，大多数符号挤在中间 4 个电平，实际没用满 64QAM。
  追问来源时承认"不是交接文档或参考仓库的公式，是我在重写量化器时引入的错误"（混淆了单分量 RMS 与复符号 RMS）。
- **结果**：旧的 200 轮结果作废、重训；这是部署模型训练流程的起点。

### 9. 累加器位宽："你算了不会超过 24 位，为什么不用 24 位？"

- **出处**：同上，09-24 23:21–23:29。
- **AI 的做法**：W8A8 时先说激活用 int16，被指出后改为 int8 激活但"累加保留 int32"；被追问"你有没有算过累加需要多少位"后才算出最坏
  4,718,592，24 位即够。
- **结果**：后续 RTL 不再用固定的 32 位，而是逐层按 $B_x+B_w+\lceil\log_2(K_hK_wC_i)\rceil+1$ 配置累加位宽。

### 10. 汇合 FIFO 深度与 XPM 原语

- **出处**：`codex/DeepJSCC-Q-FPGA-docs_2026-09-29_*.md`，09-29 12:33 – 09-30 08:36。
- **提示**：参赛者："汇合 FIFO 的深度能精确算出来吗？……另外一条路径的延迟是完全确定的啊"；"消耗多少 RAM 还得等综合出来？
  综合出来和你规划不一样就认了？"；"异步 FIFO 不要自己写，直接用 xpm 原语"，"放着 `xpm_fifo_axis` 不用非要自己再去写？"
- **AI 的做法**：先等综合结果再报 RAM 用量；综合出 105 BRAM36 + 3 URAM，与规划不符。
- **结果**：改为综合前由规划器算定（编码器 97.5 BRAM36 + 4 URAM，解码器 99.5 + 18），综合只用于核对；不符的原因是汇合 FIFO 没有按规划迁入 URAM，修正生成器后与最终 OOC 结果一致（`report/design_report.md` 4.1 节）。跨时钟域改用 XPM 原语。

### 11. 论文的立意：PPA 与统一口径

- **出处**：`codex/DeepJSCC-Q-FPGA_2026-10-03_*.md`，10-02 15:17 – 10-03 15:52。
- **AI 的做法**：先做了一轮代码审查（被告知"我是让你写论文的"），随后没有询问论文要写什么就直接成稿，没有 PPA 分析。
- **纠错**：参赛者："你有没有问过我论文写什么内容？……有没有发现我的工程和 FPGA 那篇论文的网络结构根本都不一样？"并说明对比论文的用途：一是参考其组织方式，二是作为对比对象，"不能仅仅对比帧率……最好转换成统一的 MAC/s，再进行对比，
  重点在于如何选择合适的微架构，来优化 PPA"。
- **结果**：论文与本报告 4.1、4.5 节都按名义 MAC、资源绝对量、口径边界来写对比。

## 四、系统集成与测量（Claude Code）

### 12. TX 偶发卡住：从猜测到 A/B 实验

- **出处**：`claude/AD9361_d69a7c9d.md`，10-02 11:49–11:59。
- **AI 的做法**：先断定是"数据卡住"，要改 RTL。
- **纠错**：参赛者："为什么不先软件控制 sleep 几秒后再发数据？你就这么确定是因为数据卡住了？"又补充观察："你执行命令的那段时间 LED
  一直不亮，执行完成后才亮。"
- **AI 的修正**："你说得对，我前面的判断站不住，下结论太早了。"随后设计 A/B 实验（加载后不发数据 / 立即发 PRBS），
  实验否定了自己"校准期间送数据干扰校准"的第二个猜测，并主动列出两处自己操作上的错误（后台进程没重定向 stdin、`pkill -f` 杀掉了自己的 shell）。
- **结果**：参赛者决定"先跑第 1 项，不要做第 2 项，这些东西本就不该由软件控制"，先打通端到端图像链路（板上 PSNR 与仿真一致）。

### 13. 显示问题：AI 无法观测硬件时的局限

- **出处**：`claude/AD9361_d69a7c9d.md`，10-04 02:32 – 10-05 01:21。
- **过程**：触摸屏经 Mini DP 转 HDMI 不显示；AI 依次尝试显示模式、HDMI OUT 自建工程、官方 overlay、对照原理图，
  最后建议"换一个别的转换芯片的主动式转接头"。
- **纠错**："你这么确定换主动式 Mini DP 转 HDMI 转接头能好，不花你的钱你不心疼。"AI 承认"没有任何证据证明换一个转接头芯片就一定能好"，
  改为提出零成本的对照实验（用另一块板的 HDMI IN 当"示波器"）。
- **结果**：最终换一块屏幕后正常显示。这个案例说明：在 AI 看不到物理现象时，它容易连续给出未经验证的新假设，花钱的建议尤其需要证据。

### 14. AGC 看门狗：不要依赖会随环境漂移的绝对门限

- **出处**：`claude/AD9361_caed093a.md`（10-07 04:04 前）、`claude/DeepJSCC-Q_f63b5e40.md`（10-07 04:17–05:03）。
- **过程**：基于 RSSI 底噪门限的看门狗反复修改仍误复位，参赛者："你的看门狗修了多少遍了？修好过没有？"新会话中提出原则：
  "不要按实时测到的底噪去设置什么绝对门限，信道一变就彻底失效了"，并把问题化简为"AGC 没跟上衰减会出现什么情况？1.PHY 同步不上；
  2.同步上了但功率很小"。
- **结果**：判据改为"同步率 + 增益"（只读 PL 计数器，不碰基带）。之后在案例 15 的锁定电平修复中，AI 又因复测中一次恢复时间 3.11 s 超过**自己设定的** 2.5 s 而回退了修复，
  参赛者："2.5 s 是谁定的？"——AI 的自定判据不应被当作规格机械执行（`report/notes/agc_notes.md`）。

### 15. SSCC 悬崖区异常：领域知识给出方向

- **出处**：`claude/DeepJSCC-Q_f63b5e40.md`，10-07 06:10–07:30。
- **过程**：AI 排查测量方法时进展缓慢，参赛者："你知道 AGC 为什么会解锁吗？……JSCC 训练时做了星座熵约束，PAPR 不会很高；SSCC 没这一项，
  所以 PAPR 高，峰值过载了。你算一下 JSCC 和 SSCC 好帧的 PAPR 不就知道了。"AI 随后先提出关闭过载解锁（被问"你确定改了之后其它功能不受影响？"后承认会影响小幅增强信号时的恢复）；又错说"大过载没有计数器"（被问"大 LMT 怎么可能没计数器？你猜 large 是什么意思？"）；并且只单独调高过 ADC 门限（58 → 62，台阶仍在）就把 ADC 标为"不是它"。参赛者："有没有可能这两个门限是一起工作的……你到底有没有试过同时调两者"。AI 承认两个检测器是"或"的关系，重读数据后确认：LMT 调到上限台阶仍在、ADC 调到 64 台阶消失。
- **结果**：确认是大 ADC 过载（两个条件是"或"的关系），把 AGC 锁定电平 −12 → −14 dBFS，台阶帧 9/45 → 0/44，SNR 反而提高 0.1–1.9 dB。
  AI 曾说"不影响 SNR"而未测量，被追问"什么叫不影响 SNR"后补做了 A/B 测量。

### 16. 测量口径的公平性

- **出处**：`claude/DeepJSCC-Q_f63b5e40.md`，10-07 09:00–09:26。
- **AI 的做法**：在 PS 上按到达时间统计时延与帧率，并把 SSCC（JPEG 在 PS 上）一并比较。
- **纠错**："我的设计重点是 PS 端吗？……为什么要把 PS 端的调度问题算进 FPGA 的时延、帧率抖动？公平吗？"并要求读 GLOBECOM 2025 论文看其测法；
  "从信源到射频全在板上进行，怎么测？"
- **结果**：改为两板 PS 轮询 PL 帧计数器、按数据流因果窗口配对，按论文分三段（编码 38.20 / 传输 2.87 / 解码 30.39 ms）；
  SSCC 只比较画质，不比较时延。

## 五、两个模型之间的交叉审查（2026-10-07）

### 17. Codex 起草网络章节，Claude Code 核对；Codex 再审查全文

- **出处**：`claude_codex/`（任务书、Codex 原稿、合稿后版本、审查结果与处理表）。
- **过程**：
  1. Claude Code 写任务书，要求 Codex 起草网络部分，"只用你工作区里真实存在的数据……不要编数字"；Codex 交稿后，Claude Code 用 manifest
     独立重算 ΣP、BRAM / URAM 规划等关键数，全部一致，再把引用仓库外路径的脚注改为仓库内文件。
  2. Claude Code 请 Codex 只读审查全文，Codex 列出 21 条问题，全部成立。其中 5 条是 Claude Code 自己写的部分的过度结论或无出处数值：
     "10 min 无丢帧"（只有接收计数，无逐帧证据）、"同功率"（无校准记录）、熵正则与 PAPR 的因果（无消融）、看门狗"不随环境失效"、
     64QAM 判决余量 ±4.7°（取自演示视频面板，Claude Code 按纯相位旋转独立推导为 7.7°）。
- **要点**：同一个模型很难发现自己写下的过度结论；让另一个模型对照仓库逐个数值核查，是成本很低的校验手段。

## 小结：分工模式

| 环节 | 参赛者 | AI |
|---|---|---|
| 目标与约束 | 指标（30 fps、683 符号帧、W8A12、DSP48E2 位宽）、模块边界（AGC 不碰基带、缓冲归 PHY）、公平性口径 | 把约束落实为方案并估算资源 |
| 关键判断 | 半采样相关峰、PAPR 与熵约束、过载门限的"或"关系、顺序读权重可用位宽转换 | 推导、计算、实现与验证 |
| 证据 | 物理观察（LED、屏幕、天线）、接线与上电 | 抓数据、写测量脚本、做 A/B 实验、出图 |
| 纠错 | 追问依据（"你确定吗""谁定的""你真的看了吗"） | 承认、撤回、补测；把教训写入记忆与文档 |

AI 反复出现的问题：没有证据就下结论、把自己定的经验值当规格、没有问清约束就自行加设计、只看了一部分资料就引用。
对应的协作约定（"改动要小而有判据，一次只改一处""先定验证标准""不要无必要改 RTL"）见交接文档与 `report/notes/`。
