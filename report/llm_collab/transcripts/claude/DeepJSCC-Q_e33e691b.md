## 建议方案：统一 W16A16

- **权重 16 位**，接 DSP 的 B 口（18 位）；**激活 16 位**，接 A 口（27 位）。缩放因子按每个输出通道单独取，不要求是 2 的幂。
- **全网统一位宽**，RTL 只需要一种计算单元，逐层流水实现最简单。
- 16 位量化的误差在 1e-5 量级。**预计训练后直接量化（PTQ）就够了**，QAT 留作备用。主要的误差来源会变成非线性函数的近似（sigmoid、rsqrt、sqrt），这些要单独设计和验证。
- **解码器输入**直接接你的 12 位 Q10：把它当作缩放因子为 2⁻¹⁰ 的 16 位激活，不需要重新量化，完全精确。
- **编码器输出**做 QAM 判决：用整数和 7 个门限比较，得到 3 bit 电平号，结果是精确的。

## 操作数位宽的约束点（你的第 1 条要求）

W16A16 下有几处中间结果会超过 27 位，必须先移位再乘：

| 位置 | 问题 | 做法 |
|---|---|---|
| **重量化** | 3×3×32 卷积的累加值约 39 位，不能直接乘 18 位的系数 M | 累加值先带舍入右移到 ≤27 位，再乘 M（≤18 位），再移位、饱和成 16 位。先截掉的是输出精度以外约 11 位的余量，误差可忽略 |
| **GDN** | x² 是 32 位，要乘 γ（≤18 位） | x² 先右移到 ≤27 位，再乘 γ。求和结果进 rsqrt 查表（先规格化，查表输出 ≤18 位），再乘 x（16 位） |
| **注意力门控** | a（16 位）× σ（≤18 位） | 位宽已在范围内 |
| **偏置** | 需要加到累加器上 | 走 48 位累加器的 C 口，不经过乘法器 |
| **LeakyReLU** | 需要乘 1/128 | 对累加值做 x ≥ 0 ? x : x >>> 7，用逻辑实现，不占 DSP |

## sqrt、GDN 和逆 GDN：逐位迭代，不用 DSP

- **sqrt**：用逐位（移位加减）的整数开方，只占 LUT 和 FF。它的结果等于 floor(√D)，在黄金模型里用 Python 的 `math.isqrt` 就能逐比特对齐。
- **GDN**：y = x / √D，其中 D = β + Σγx²。先开方，再用移位减法的迭代除法器，同样不用 DSP。
- **逆 GDN**：y = x · √D，开方后乘 x，占 1 个 DSP（x 是 16 位，√D 截到 ≤ 18 位）。
- **位宽**：要让 √D 有足够的有效位，D 需要约 28 位小数，总宽 36–40 位；开方输出 18–20 位，也就是迭代 18–20 次。具体宽度要等 PTQ 标定出每层 D 的实际范围后再定。
- **舍入**：多算一位就能从向下取整变成四舍五入，黄金模型同样可以精确对齐。

## sigmoid：分段线性（不用 CORDIC）

CORDIC 做 sigmoid 要先用双曲 CORDIC 算出 e^x 或 tanh，最后还得再做一次除法，比分段线性更贵，所以我不推荐。建议的做法：
- **利用对称性**：σ(−x) = 1 − σ(x)，只需要近似 [0, 8) 这一段；x ≥ 8 时直接输出 1。
- **均匀分段**：用 |x| 的高位做段号，每段存斜率和截距（各 ≤ 18 位），用 1 个 DSP 算"斜率 × 段内偏移 + 截距"。
- **系数放寄存器或分布式 LUT**：32 段 × 36 位只有约 1.2 Kb。同一层内部是分时复用的，只需要一个读口，不占 BRAM。
- **精度估算**：线性插值的最大误差约为 h²·max|σ''|/8，其中 max|σ''| ≈ 0.096。
  - 16 段（h = 0.5）：约 3e-3，够 8 位像素输出（1/2 LSB ≈ 2e-3，基本合格）。
  - 32 段（h = 0.25）：约 7.5e-4，约 10 bit 精度。
  - 64 段（h = 0.125）：约 1.9e-4，约 12 bit 精度。
- **段数怎么定**：最终输出 sigmoid 预计 32 段足够；注意力门控的输出要乘上另一个分支再重量化，大概率 32 到 64 段就够。最终用敏感性测试决定。

## 汇总：非线性单元的实现

| 单元 | 实现方式 | DSP | BRAM |
|---|---|---|---|
| sqrt | 逐位迭代，18–20 级 | 0 | 0 |
| GDN 中的除法 | 移位减法迭代 | 0 | 0 |
| 逆 GDN 中的乘法 | 乘法器 | 1 | 0 |

| LeakyReLU | 在累加器上判符号再右移 7 位 | 0 | 0 |

## 关于 QAM 判决约 1% 不一致

整数编码器输出的 QAM 电平和浮点版有约 0.9% 的符号不一致，我查清了原因：
- PyTorch 在 CUDA 上默认用 TF32 做卷积，这种"浮点"和 float64 的偏差（中位数 4.5e-4）与 int16 和 float64 的偏差（中位数 6.1e-4）在同一量级，两者造成的判决翻转也差不多（0.27% 对 0.28%）。
- 原因是编码器本身会放大微小扰动，**int16 的精度已经和 GPU 上的 float32 推理相当**。翻转都发生在判决门限附近，所以对 PSNR 没有影响。
- 对 RTL 验证的含义：**黄金向量必须用整数参考模型生成，不能拿浮点输出做逐比特比对**。

## 整数参考模型的实现（[int_ref.py](int_ref.py)）

浮点后端和整数后端共用同一份网络结构描述。整数后端的每一步都对应一个 RTL 操作，所有中间值都检查过在 2⁵³ 以内，保证计算精确。

| 操作 | 整数实现 | DSP 操作数 |
|---|---|---|
| 卷积 | int16 权重（按输出通道缩放）× int16 激活，48 位累加，偏置在累加器上加入 | 16 × 16 |
| LeakyReLU / ReLU | 在累加器上判符号：负数右移 7 位（带舍入）/ 置 0 | 不用 DSP |
| 重量化 | `sat16(rsr(sat27(rsr(acc,pre))·M, sh))`，M < 2¹⁷ | 27 × 17 |
| 残差加 | `sat16(rsr(qa·Ma + qb·Mb, sh))` | 16 × 17 |
| GDN / 逆 GDN | D = (β + Σγ·rsr(x²,4))·2^L；r = isqrt(D)（逐位迭代）；GDN 的 t = sign·⌊\|x\|·2^F/r⌋ 用迭代除法，逆 GDN 算 x·r，最后都重量化 | x² 截到 26 位 × 15 位 γ；r（≤ 23 位）× x |
| sigmoid | \|z\| 换成 Q3.12，32 段分段线性，输出 Q0.16，负半边用 1−σ | 17 × ≤ 11 |
| 注意力门控 | x + rsr(a·g, 16) | 16 × 17 |
| 输出像素 | clamp(rsr(g·255, 16), 0, 255) | |
| QAM 判决 | 和 7 个整数门限比较 | 不用 DSP |

表中 rsr 是带舍入的算术右移。实测最宽的内部信号：
- GDN 的 D 最多 46 位，开方需要迭代 23 次；
- 重量化的乘积最多 43 位；
- 都在 48 位累加器以内。

## Chisel 能否精确控制 RAM 类型

**能，但不是靠 Chisel 自己的存储器语法。**
- **`SyncReadMem` / `Mem` 做不到**：生成的是行为级存储器数组，最终用什么 RAM 由 Vivado 推断决定。想加 `(* ram_style = "ultra" *)` 这类属性，要通过 FIRRTL 注解传到 firtool 生成的 Verilog 里，而且不同版本支持程度不一样，不够可靠。
- **可靠的做法有两种**：
  1. 把 Xilinx 的 XPM 存储器（如 `xpm_memory_sdpram`，参数 `MEMORY_PRIMITIVE = "ultra" / "block" / "distributed"`）包成 BlackBox 来实例化，这样能精确指定类型、位宽、深度和读延迟；
  2. 用 firtool 的 `--repl-seq-mem` 把所有存储器替换成外部模块，再自己写包装去例化 XPM。
- DSP48E2 也一样：可以依赖推断（流水寄存器要写对），要精确控制就直接例化原语。

所以"精确控制存储器"在两种语言里做法一样：**都是直接例化 XPM 或原语**。它不是选择语言的依据。

## 为什么建议 SystemVerilog

1. **和你现有的工程一致**：接收机已经按 MATLAB 写好了 RTL，最后编码器和解码器都要和 PHY 放在同一个 Vivado 工程里集成。
2. **调试和时序收敛更直接**：Chisel 生成的 Verilog 信号名是编译器改写过的，而且会把逻辑拆散、合并。看时序报告、加 ILA 抓信号、按报告改关键路径时都要来回对照。你们要在 250 MHz 下收敛 43 位乘积、46 位开方这类宽数据通路，这一点影响很大。
3. **工具链更简单**：Chisel 需要 Scala、sbt、firtool 配套，版本兼容性问题不少。SV 用 Vivado 就够了。
4. **Chisel 的主要优势可以用别的方式拿到**：这个网络有约 70 个卷积层，形状和并行度各不相同，非常适合"生成器"式写法，这确实是 Chisel 的长处。但可以这样替代：
   - **手写一小组参数化的 SV 核心模块**：卷积引擎、行缓冲、重量化、GDN/逆 GDN（开方加除法）、分段线性 sigmoid、残差加、PixelShuffle、延迟对齐 FIFO。
   - **用 Python 生成顶层网络**：读导出时的那份 `manifest.json`，生成层的例化、连线、每层并行度和 `.mem` 路径，以及每块存储器的 RAM 类型（URAM / BRAM / LUTRAM 就按上面的分配结果写进去）。
   - 这样 **manifest 是唯一的数据来源**：整数参考模型、黄金向量和 RTL 顶层都从它来，不会出现参数对不上的问题。

## 验证怎么配合

- **逐层对比**：测试平台用 `$readmemh` 读输入和黄金 `.mem` 文件，逐层逐元素比较，要求完全一致。
- **用 cocotb 更方便**：可以直接调用 Python 的整数参考模型，随机图像、随机噪声都能批量跑。cocotb 配 Verilator 或 Questa 可以用，但**不支持 Vivado 自带的 xsim**。
- **XPM 的仿真问题**：Verilator 不一定能编译 XPM 源码，可以在仿真时用 `ifdef` 换成行为级 RAM 模型，综合时再换回 XPM。

## 什么情况下选 Chisel

如果没有这个基础，为这一个项目引入 Chisel 不值得。

## 其实不需要一次读完所有通道

在 250 MHz、30 fps 下，每个像素能用的时钟周期很多：

| 位置 | 分辨率 | 每个像素可用的周期数 |
|---|---|---|
| 编码器输入、解码器输出 | 256×256 | 约 127 |
| 第一次下采样后 | 128×128 | 约 508 |
| 深层 | 64×64 | 约 2034 |

卷积引擎用 P 路乘法并行算 P 个输出通道时，激活值是广播给所有路的，每个周期只需要读 1 个。所以一个像素的通道即使分几个周期读出，也远远用不完时间预算。

## 建议：一个 72 位字放 4 个通道

- **组织方式**：BRAM36 用 512×72 模式，每个字放 4 个通道的 16 位激活。32 通道分 8 个字，16 通道分 4 个字，存在连续地址上。
- **读出时间**：读一个像素的全部通道只需 **C/4 个周期**（32 通道 8 个周期）。最紧张的 256×256 层有 127 个周期，余量十几倍。
- **存储效率**：BRAM 深度能用满，行缓冲回到按通道逐个读时的水平。上一次的分配结果（BRAM36 用 54% 到 60%、URAM 用 38% 到 58%）基本不变。
- **地址计算简单**：地址 = 像素号 × (C/4) + 字号，完全符合 NHWC 顺序，和导出的 `.mem` 文件一致。
- **想更快的话**：两块 BRAM 并排成 144 位字，一次读 8 个通道，32 通道 4 个周期读完。BRAM 块数会翻倍，但仍然放得下。

## 顺带一个免费的选项

72 位正好装得下 4 个 18 位数，BRAM 的校验位本来就可以当数据位用。所以**激活可以从 16 位放宽到 18 位，存储零额外开销**。DSP 这边激活接 27 位的 A 口，也没问题。不过从 PTQ 结果看，16 位已经只差约 0.01 dB，放宽到 18 位没有实际收益，这里只是说明有这个余地。

我的建议是：**激活保持 16 位，存储器按每个 72 位字 4 个通道组织**。如果你的数据通路确实需要一个周期拿到整个像素，那只在个别关键层用 LUTRAM 做宽缓冲，不要全网都这样做。

| 位宽 | 余量 | 验证集 | Kodak | Kodak 上的饱和 |

- **余量的取舍**：在 12 位下，余量取 2 倍会少 1 位分辨率，但换来零饱和，两者只差约 0.01 dB。我建议正式导出时取中间的 **1.5 倍**，或者只给出现饱和的解码器最后两块单独留 2 倍。用最终模型时两种都测一下再定。

## 存储：每个 72 位字 6 个数

两种位宽都按每周期读一个激活、3×3 卷积用 3 行环形缓冲来算：

| | W16A16（每字 4 个） | **W12A12（每字 6 个）** |
|---|---|---|
| 编码器 BRAM36 | 94 / 144（65%） | **66 / 144（46%）** |
| 编码器 URAM | 27 / 64 | **24 / 64** |
| 解码器 BRAM36 | 105 / 144（73%） | **78 / 144（54%）** |
| 解码器 URAM | 42 / 64 | **37 / 64** |
| DSP 路数（编码器 / 解码器） | 208 / 298 | 208 / 298 |

URAM 下降得不多，因为大层的权重存储块数主要取决于要并行读出多少个权重，而不是容量。每块存储每周期能出 2 个端口 × 6 个 = 12 个权重。

## 12 位打包的实现细节

- **跨像素连续打包**：通道数是 3、8、12、16、32、128，大多不是 6 的倍数。如果每个像素从新字开始存，8 通道的利用率只有 67%。要把 72 位占满，就要按 NHWC 展平后连续打包：
  - 元素序号 = (行·W + 列)·C + 通道；
  - 字地址 = 序号 / 6，字内位置 = 序号 % 6。
  - 因为每周期只顺序读一个，这两个值都可以用计数器递增得到，不需要除法器。
- **导出格式相应调整**：`.mem` 仍然每行一个 12 位值（3 位十六进制），打包由 RTL 生成脚本完成。如果你希望直接导出打包好的 72 位字（18 位十六进制），告诉我一声。

## 使用时要注意

1. **符号顺序是扰码之前的**：`latent_idx` 和 `rx_symbols` 都按模型定义的顺序排列：latent 按 NCHW 展平后，相邻两个元素组成一个符号 (I, Q)。
   - 编码器输出和解码器输入这两处，RTL 都要按这个顺序做整帧重排。编码器侧是 NHWC 数据流，同一符号的 I、Q 相隔 C 个元素。
   - 你 PHY 里的符号级扰码和交织在这之外单独做。
   - 黄金模型里有从 `rx_symbols` 重建 `rx_in` 的代码，可以直接参考。
2. **卷积没有合并导出**：上采样块的主路和旁路卷积、带步长残差块的 conv1 和旁路卷积仍然是各层独立的文件。要合并成一个引擎，就在 RTL 生成脚本里把两层的权重按输出通道拼起来；两者的重量化参数本来就是按通道存的，直接拼接即可。
3. **每行一个数，没有打包成 72 位字**：每字 6 个数的打包留给 RTL 生成脚本做，这样逐层比对最直接。用 `$readmemh` 读时，按对应位宽的寄存器读入，补码自然就对了。
4. **黄金模型的比对方式**：[golden_np.py](golden_np.py) 是逐算子比对，每一层都以黄金向量作为输入，所以一处出错不会一路传下去。以后调试 RTL 时，可以用它对单独一层做"输入 → 输出"的检查。
